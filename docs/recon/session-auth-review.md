# Security review: session-cookie authentication (nextcloud-dav)

**Date:** 2026-09-20/21. Adversarial review of commit `0269537` (working tree
clean except this file). The running harness sidecar binary
(`target/release/nextcloud-dav`, built 2026-09-20 23:06) is newer than every
source file, so all live tests below exercise exactly the code under review.

**Scope:** `src/auth/session.rs`, `src/auth/session_redis.rs`,
`authenticate_session` + `classify_session_token_state` (`src/auth/mod.rs`),
the four call sites in `src/routes.rs` (`handle_calendars`, `handle_discovery`,
`handle_files`, `handle`), and the DB lookups they use (`authtoken_by_hash`,
`native_user_exists`, `user_is_disabled`, `auth_token_from_row`).

**PHP reference (Nextcloud 33.0.5, same code in the server repo and the
harness container):** `apps/dav/lib/Connector/Sabre/Auth.php`,
`lib/private/User/Session.php`, `lib/private/Authentication/TwoFactorAuth/Manager.php`,
`lib/private/AppFramework/Http/Request.php`, `lib/private/Security/Crypto.php`,
`lib/private/Security/CSRF/*`, `lib/private/Authentication/Token/PublicKeyTokenProvider.php`,
`lib/private/Session/{CryptoWrapper,CryptoSessionData}.php`,
`lib/private/Lockdown/LockdownManager.php`, `lib/private/User/User.php`,
`lib/private/Config/UserConfig.php`, `lib/OC.php`
(`performSameSiteCookieProtection`), `lib/private/Security/SecureRandom.php`.

**Method:** line-by-line comparison with the PHP sources; `cargo test --lib`
(203/203 pass, incl. the PHP-produced crypto vector); the pre-existing harness
matrix `tests/local/session_auth.sh` (evidence: 54/54 PASS); plus new
adversarial A/B runs against the disposable `ncdav-e2e-*` stack — same request
sent to PHP (127.0.0.1:18081) and to the sidecar (127.0.0.1:17870), synthetic
session fixtures built with PHP's own `OC\Security\Crypto`, **sidecar queried
before PHP** (a PHP request rewrites or destroys the session, which silently
invalidates the comparison). Transcript: `tests/local/state/evidence/session-auth-review.txt`.

## Findings

### F1 — HIGH — cookie values are decoded with PHP's *GET* semantics: a raw `+` in the passphrase breaks the sidecar for ~87 % of browsers
* **Where:** `src/auth/session.rs:295` (`cookie_value` → `crate::util::urldecode`)
  and `src/util.rs:30-32` (`urldecode` = percent-decode **after `+`→space**).
* **What:** PHP populates `$_COOKIE` with **rawurldecode** semantics —
  percent-decoding only, `+` preserved. Proved empirically in the harness
  (PHP built-in server): `Cookie: oc_sessionPassphrase=AAA+BBB%2FCCC%2BDDD`
  yields `len=15 plus=2 slash=1` — the `+` survives, `%2F` decodes.
  The sidecar instead applies `+`→space to every cookie value.
* **Why it matters:** the passphrase cookie value is generated by
  `CryptoWrapper` as `$random->generate(128)` over the alphabet
  `A-Za-z0-9+/` (`SecureRandom.php:23`) and set with plain `setcookie` —
  no encoding. A real browser stores and re-sends it **verbatim**, so a
  literal `+` reaches the server as `+`. The sidecar then computes the
  passphrase with a space in its place → HMAC fails → delegate. PHP decrypts
  fine. P(no `+` in 128 chars of a 64-symbol alphabet) = (63/64)^128 ≈ 13 %,
  so **~87 % of browsers carry a `+` in their passphrase and get *every*
  session-auth request delegated** — the feature silently degrades to PHP
  speed with no error anywhere. Fail-closed (no bypass), but it defeats the
  feature's purpose and is invisible to curl-based tests (curl percent-encodes
  `+`/`/` in cookie values, which is exactly why the 54-check matrix and all
  earlier curl tests passed).
* **Triggering input (live, confirmed):** synthetic session encrypted with a
  passphrase containing `+` and `/`; request with the passphrase cookie sent
  raw (`+` literal): **PHP 207, sidecar 501**; the same value percent-encoded
  (`%2B`/`%2F`): PHP 207, sidecar 207.
* **Minimal fix:** decode **cookie** values with percent-decoding only
  (rawurldecode); keep `+`→space for **query** parameters only (`$_GET`
  semantics — `query_param` is currently correct).

### F2 — MEDIUM — PHP's global strict-cookie gate (412) is not reproduced: the sidecar accepts requests PHP refuses
* **Where:** `src/auth/session.rs:246-283` (`decision_after_token`) and
  `src/auth/mod.rs:342-343` — the strict/lax same-site cookies are required
  only for branch 1 with a non-exempt method.
* **PHP:** `OC::performSameSiteCookieProtection()` (`lib/OC.php:571-632`) runs
  for **every `remote.php` request that carries any cookie**: unless the user
  agent matches `csrf.optout` (default `WebDAVFS`, `Microsoft-WebDAV-MiniRedir`)
  or `debug` is on, PHP requires `passesStrictCookieCheck()` — strict cookie
  `=== 'true'` **and** lax `=== 'true'` (name chosen by
  `getProtectedCookieName`, i.e. the `__Host-` variant when secure+path=/) —
  and answers **412 "Strict Cookie has not been found in request"** otherwise,
  *before* the DAV plugin, regardless of method, 2FA, `DAV_AUTHENTICATED`, or
  anything else.
* **Divergence:** the sidecar accepts (207, `x-nextcloud-dav: sidecar`) a
  fully valid session on branch 2, and on branch 1 for GET/HEAD/OPTIONS,
  **without any same-site marker cookies**, where PHP hard-fails with 412.
  Confirmed live (synthetic branch-2 session, only the session+passphrase
  cookies sent): **PHP 412, sidecar 207**.
* **Exploitability:** the gate is NC's second CSRF/anti-cookie-replay layer,
  aimed exactly at "broken webdav clients" that resend partial cookie sets.
  An attacker who obtains the (httponly) session id + passphrase — e.g. from
  a proxy log, a dumped cookie jar, or a client that stored only those two —
  is **blocked by PHP but served by the sidecar**. Not a from-scratch bypass
  (both cookies must already be possessed), but a real removal of a defense
  layer on the sidecar-accepted paths.
* **Minimal fix:** require the strict+lax same-site cookies (matching PHP's
  name selection) for **every** session-cookie acceptance, or delegate when
  they are absent; mirror the `csrf.optout`/debug exemptions only if parity
  of those edge cases matters.

### F3 — MEDIUM — `app_password` type confusion silently swaps the validated token and skips 2FA (confirmed: sidecar accepts, PHP logs out)
* **Where:** `src/auth/session.rs:59-86` (`SessionPayload::parse`) and
  `src/auth/mod.rs:319-325` (step 6).
* **What:** `has_app_password` is true for any present, non-null JSON value
  (number/array/bool included — this faithfully matches PHP's `isset`), but
  `app_password` is `Some` only for strings. With a non-string value the 2FA
  gate is skipped (step 7 tests `has_app_password`) while the token to
  revalidate silently becomes **the session id** (`None => session_id` arm),
  which for a browser session is a perfectly valid TEMPORARY token.
  PHP's `validateSession()` (`User/Session.php:203-228`) instead puts the
  non-string into `validateToken()` → `getToken()` → `InvalidTokenException`
  (short/coerced value) → **`logout()`**; a JSON array is a PHP TypeError.
  PHP never authenticates such a session.
* **Confirmed live (T1):** synthetic session with
  `"app_password": 123456789012345678901234567890` (number), no
  `two_factor_auth_passed`, no `DAV_AUTHENTICATED`, valid requesttoken and
  strict cookies: **sidecar 207 (`authenticated alice via Nextcloud session
  cookie`), PHP 401** (session logged out). Control: the same payload with a
  *string* `app_password` that is not a token → sidecar 501 (correct
  fail-closed), proving the acceptance is specifically the type confusion.
* **Reachability:** PHP writes `app_password` only as a string
  (`User/Session.php:459,880`), so this needs a session-content write
  primitive (direct Redis write or a future PHP bug). It is a confirmed
  accept-where-PHP-rejects waiting for a primitive, and violates the stated
  "cannot be evaluated exactly → delegate" rule.
* **Minimal fix:** in `parse`, treat present-and-non-null-but-not-a-string
  `app_password` as a parse failure → delegate. Same reasoning applies to a
  non-string `AUTHENTICATED_TO_DAV_BACKEND` (PHP: neither branch → 401;
  Rust's `Option<String>` maps it to branch 1), though that one additionally
  needs the full CSRF proof to matter.

### F4 — MEDIUM — token scope / lockdown is ignored (code-confirmed; not reproduced live)
* **Where:** `src/auth/mod.rs:127-197` (`classify_session_token_state`) and
  `src/db.rs:1105-1123` (`authtoken_by_hash` never selects `oc_authtoken.scope`);
  `SessionPayload` ignores the session's `token_scope` key.
* **PHP:** `validateToken()` ends with `$this->lockdownManager->setToken($dbToken)`
  (`User/Session.php:800`), which stores the scope and enables lockdown;
  `LockdownManager::canAccessFilesystem()` gates `SetupManager`
  (`Files/SetupManager.php:335,414,830`) — a token scoped
  `filesystem: false` gets no filesystem mounted, so PHP does not serve
  files-DAV for it. The sidecar serves files PROPFIND metadata from the DB
  regardless.
* **Triggering input:** Basic-login to DAV with a scoped app password
  (filesystem=false), keep the cookie jar, then cookie-only files PROPFINDs.
* **Impact:** file *metadata* only (content GETs are delegated). The same
  blind spot exists in the Basic fast path (`classify_token_state`), so it
  predates session auth; session auth adds a second route to it.
* **Minimal fix:** select `scope` in `authtoken_by_hash` and delegate when it
  is non-empty (or reproduce `canAccessFilesystem()`).

### F5 — LOW — requesttoken source precedence differs: header wins over query param (confirmed)
* **Where:** `src/auth/mod.rs:340` (`requesttoken_header.or(requesttoken_param)`),
  `src/auth/session.rs:246-283`.
* **PHP:** `Request::passesCSRFCheck()` (`Request.php:440-447`) prefers the
  **GET param**, then POST param, then the header. With a valid header token
  and a bogus `?requesttoken=…`, PHP's check fails → 401; the sidecar accepts
  via the header. Confirmed live (T2, synthetic branch-1 session, strict
  cookies, valid header + `?requesttoken=bogus-param`): **PHP 401,
  sidecar 207**.
* **Impact:** marginal — the requester must already possess the valid token —
  but it is a literal accept-where-PHP-rejects.
* **Minimal fix:** evaluate the query param first (like PHP), or delegate when
  both are present and only one is valid.

### F6 — LOW — `user_is_disabled` is a blacklist; PHP's `isEnabled` is a whitelist (confirmed)
* **Where:** `src/db.rs:1138-1151` vs `User/User.php:472-486` +
  `Config/UserConfig.php:723-727` (enabled only for `1/true/yes/on`,
  case-insensitive).
* **A stored `core/enabled` value of `'0'`, `'off'`, `''` or garbage leaves
  the account *enabled* for the sidecar and *disabled* for PHP.** Confirmed
  live (T3): row `(alice, core, enabled, '0')` → **PHP 401, sidecar 207**;
  after restoring the row the sidecar still served (control 207). Not
  produced by `setEnabled` (writes `'true'/'false'`), so it needs manual SQL
  or a foreign writer.
* **Minimal fix:** invert — disabled unless the value is one of
  `1/true/yes/on` (absent row = enabled).

### F7 — LOW — same-site cookie accepted under both the plain and `__Host-` names
* **Where:** `src/auth/session.rs:305-318` vs `Request.php:474-487`
  (`getProtectedCookieName` picks exactly one name from the session cookie
  params). When the instance is HTTPS (PHP looks only for
  `__Host-nc_sameSiteCookiestrict`), a plain `nc_sameSiteCookiestrict=true`
  settable by a sibling subdomain satisfies the sidecar but not PHP.
  Exploitability is marginal (a valid requesttoken is still required and the
  session cookie itself is SameSite=Lax), but it widens F2's gate.
* **Minimal fix:** choose the name the way PHP does (`__Host-` iff
  secure && path = `/`) and accept only that one.

### F8 — LOW — a huge RESP bulk length can abort the process
* **Where:** `src/auth/session_redis.rs:220` (`vec![0u8; len + 2]`). A
  `$<huge>` reply header from the session Redis makes the sidecar attempt a
  giant allocation → `handle_alloc_error` → abort. Only a hostile/compromised
  Redis can trigger it (trusted infrastructure); DoS, not bypass.
* **Minimal fix:** reject lengths above a sane cap (sessions are a few KB).

### F9 — LOW — an unparseable `?database=` silently selects DB 0
* **Where:** `src/auth/session_redis.rs:99` — `value.parse::<u32>().ok()`
  leaves `database = None` (no `SELECT`) on parse failure, whereas PHP errors
  out on a broken save_path. Operator-controlled input only, but it violates
  the file's own "fail closed" rule.
* **Minimal fix:** `return None` when a `database`/`db` value is present but
  unparseable.

### F10 — NIT — duplicate cookie names: sidecar takes the first, PHP the last
* `cookie_value` (`session.rs:284-299`) returns the first match; PHP's
  `$_COOKIE` keeps the last. Only observable with duplicate cookie names
  (subdomain shadowing); it selects which *valid* session is used, never
  grants anything beyond that session's own user.

### F11 — NIT — PHP-lenient CSRF token decoding is (safely) not reproduced
* `decrypt_requesttoken` (`session.rs:118-146`) is strictly narrower than
  `CsrfToken::getDecryptedValue()`: STANDARD base64 (PHP's non-strict decode
  silently drops invalid chars), equal lengths, valid UTF-8. Every input PHP
  accepts and Rust rejects delegates — fail-closed. `explode(':')`-vs-`split`
  semantics match case by case (`a:b:` → 3 parts → invalid in both; `:b` →
  cannot equal a non-empty session token in either).

### F12 — INFO — PHP-only leniencies the sidecar does not reproduce (all fail-closed: delegate)
* `OCS-APIRequest` header short-circuits `passesCSRFCheck()` to true
  (`Request.php:434-436`).
* Official desktop/android/iOS user agents skip `requiresCSRFCheck()`
  (`Auth.php:127-134`); WebDAVFS/MiniRedir opt out of the strict-cookie gate.
* `session['app_api'] === true` also skips 2FA (`Manager.php:272`).
* v2 ciphertext format and uppercase (`ctype_xdigit`) hex in
  `Crypto::decryptWithoutSecret`; the sidecar only matches lowercase v3.
* Non-native (LDAP/SSO) users: PHP authenticates their sessions; the sidecar
  requires an `oc_users` row and delegates otherwise.
* PHP accepts branch 1/2 even with an `Authorization` header present (branch 1
  has no `empty(Authorization)` clause; branch 2 requires it); the sidecar
  delegates whenever the header exists (`routes.rs:473-475`).
* A form-encoded body `requesttoken` for non-GET/POST methods
  (`Request.php:404-411`) — the sidecar reads only header/query and delegates.
* **Warm-up:** `two_factor_auth_passed` is only written into the session when
  PHP first evaluates `needsSecondFactor()` (DAV auth or
  `OC_Util::checkLoggedIn`). A freshly logged-in browser session that has
  never made a PHP-served DAV request delegates from the sidecar (observed
  live: fresh form session → sidecar 501; after one PHP DAV 207 → sidecar
  207). Fail-closed; inherent to the design's conservative 2FA rule.

### F13 — INFO — operational notes
* **Per-request Redis connection** (`session_redis.rs:158-…`): every
  session-auth request opens a fresh TCP connection + `AUTH` + `SELECT` +
  `GET`. An unauthenticated client can force this by sending a cookie named
  like the instance id — a cheap amplification surface. Consider pooling and
  a pre-filter.
* **Session TTL:** the sidecar only reads `PHPREDIS_SESSION:<id>`; it never
  refreshes the key's TTL. If phpredis does not refresh TTL on read, a
  workload served exclusively by the sidecar could let live sessions expire
  (fails closed; availability only). Not verified.

## Verified correct

1. **Crypto exactness** (`session.rs:153-191` vs `Crypto.php`): HKDF-SHA512
   (no salt/info, 64-byte OKM — empty salt ≡ zero-block salt); HMAC-SHA512
   keyed with the ASCII-hex of `sha512(macKey || 'a')` (128 chars = SHA-512
   block size, used as-is), message `ct_hex || iv_hex`, constant-time
   `verify_slice`; AES-128-CBC with PBKDF2-SHA1(encKey32, "phpseclib", 1000,
   16). Verified against a real `OC\Security\Crypto::encrypt()` blob produced
   in the harness (`decrypts_a_php_produced_blob` passes) and by the 54-check
   e2e matrix.
2. **HMAC before plaintext on every path**: `decrypt_fields` verifies the MAC
   before AES; `extract_and_decrypt` returns only MAC-verified plaintext;
   parsing happens only on decrypted bytes. Empty, short, odd-length,
   non-multiple-of-16, oversized, tampered, wrong-passphrase inputs all fail
   closed (unit tests + harness D2-D5).
3. **No reachable panic**: the sole `expect` (HKDF length) is unreachable;
   `new_from_slices` lengths are fixed; all `extract_and_decrypt` indices are
   `raw.get(...)`-guarded; RESP `line[1..]` slices only after an ASCII first
   byte; PKCS#7 failure is a `Result`.
4. **Envelope scan**: zero verified candidates → delegate; **two** verified →
   delegate (confirmed live, T4: duplicated envelope with a stale igbinary
   length header → PHP 207 reading only the first, **sidecar 501, no sidecar
   header**); candidates are HMAC-gated, so attacker-chosen bytes cannot
   verify without the passphrase; cross-session replay is impossible because
   the HMAC key is derived from the per-browser random passphrase and the
   scan only sees one session's own Redis value.
5. **The ordered decision matches PHP's DAV plugin** (`Auth::auth` +
   `passesCSRFCheck` + `requiresCSRFCheck`): 2FA before the branches
   (`two_factor_auth_passed === uid` mirrors `SESSION_UID_DONE === getUID()`;
   the app-password skip mirrors `exists('app_password')`, and
   `!v.is_null()` reproduces PHP `isset` semantics exactly for JSON null);
   branch 2 (`DAV_AUTHENTICATED === uid`) without CSRF, with the
   `empty(Authorization)` clause enforced upstream; branch 1 with
   GET/HEAD/OPTIONS exemption, strict+lax+requesttoken otherwise
   (constant-time compare, `hash_equals` parity); `DAV_AUTHENTICATED` naming
   a different uid never accepts; the requesttoken de-obfuscation
   (`base64(v XOR s):base64(s)`, exactly two parts) matches
   `CsrfToken::getDecryptedValue` on the strict paths.
6. **`classify_session_token_state` vs `validateSession`/`checkToken`/
   `checkTokenCredentials`**: token choice (`app_password` if string, else
   session id — the empty-string case delegates like PHP's logout); WIPE
   rejected; expiry delegated (same client-visible outcome as PHP's
   ExpiredTokenException → logout); `password_invalid` rejected; `expires`
   NULL **and** 0 = no expiry; `last_check` NULL → 0; window strictly
   `> now-300`; fresh-window before the passwordless rule; passwordless
   accepted with a stale check; password-bearing + stale → delegate; disabled
   user rejected. The sidecar additionally requires `row.uid == session uid`
   (PHP does not — stricter, safe) and correctly omits the login-name check
   (PHP's session revalidation passes `$user = null`). Stale/revoked tokens:
   harness D9 + unit tests.
7. **Fail-closed plumbing**: every DB/Redis error, missing config, unparsable
   JSON, missing/empty `user_id`, missing Redis key, disabled or non-native
   user, failed revalidation → `None` → 501 with no sidecar header. All four
   call sites go through the single `authenticate_dav`, and every one applies
   the uid-vs-path rule (files additionally 404s a foreign home, like PHP).
8. **Cookie names/shape**: session cookie = instanceid verbatim
   (`OC_Util::getInstanceId` already carries the `oc` prefix and is used
   directly as `session_name`); passphrase cookie = `oc_sessionPassphrase`
   (`CryptoWrapper::COOKIE_NAME`), httponly+Lax in PHP; the session id needs
   no decoding (hex), and the percent-decode itself matches PHP for values
   without `+` (F1 is about `+` only).
9. **Secrets**: the session id, passphrase, payload, Redis password and app
   passwords are never logged (`RedisError` opaque; `Debug` impls redact;
   logs carry only the uid and "delegating").
10. **PHP's `$_COOKIE` decoding semantics were established empirically**
    (rawurldecode; `+` preserved) — this is what makes F1 definitive rather
    than theoretical.

## Could not verify

* **F4 (token scope) end-to-end** — no scoped token could be created in the
  disposable harness without hand-writing a token row; the divergence rests
  on code reading of both sides (`LockdownManager::canAccessFilesystem`
  gating `SetupManager`, which the sidecar never consults).
* **phpredis TTL-on-read behaviour** (F13) — would need a time-accelerated
  harness.
* **PHP's unequal-length string XOR** in `CsrfToken::getDecryptedValue`
  (padding vs truncation): only makes PHP more lenient than the Rust check,
  which rejects unequal lengths — cannot create an accept-where-PHP-rejects.
* **The form2 CLI-decrypt anomaly** — my in-container CLI scripts could not
  decrypt one specific real form session (all decode variants) while both
  PHP and the sidecar serve it fine. It is a tooling artifact (both
  authoritative implementations agree); unresolved, but it did not affect
  any conclusion above.
* **Whether any PHP code path can write a non-string `app_password` or
  `AUTHENTICATED_TO_DAV_BACKEND`** (F3's reachability): all writers found are
  `set(..., <string>)`; a complete audit of every `ISession::set` call site
  in the app ecosystem was not performed.
* **`IProvideEnabledStateBackend`-provided enabled state** for non-Database
  backends — out of scope: those users are non-native and always delegate.

### Incident note (transparency)
During debugging, two constraint slips occurred, both confined to the
**disposable harness** (never production): (a) one script printed a session
*ciphertext* blob (offset/print mix-up) — ciphertext only, the passphrase was
never printed; (b) one `bash -x` trace of a script sourcing `state/env`
revealed the harness's local docker credentials in the transcript. The
harness is torn down with `teardown.sh`; its credentials are not used
anywhere else. No real user data, production secrets, or the instance secret
were ever printed.

## Summary

No from-scratch authentication bypass was found: the crypto is a faithful,
constant-time, verify-before-decrypt reproduction of `OC\Security\Crypto`,
the envelope scan is HMAC-gated and ambiguity-refusing, the token
revalidation and the DAV-plugin decision match PHP or delegate, and every
error path fails closed. The review did surface one high-severity
**fail-closed** defect — cookie values are decoded with `+`→space while
PHP's `$_COOKIE` preserves `+`, so with the `A-Za-z0-9+/` passphrase alphabet
roughly 87 % of browsers get *all* session-auth requests silently delegated
(masked in every test because curl percent-encodes `+`) — plus three
confirmed accept-where-PHP-rejects divergences (missing global strict-cookie
gate, `app_password` type confusion, requesttoken precedence), the
unimplemented token-scope/lockdown check, and a set of lower-severity
parity and hardening items. Recommended order: fix the cookie decoding
first (one-line semantic change, restores the feature), then the strict-cookie
gate and the `app_password` type check (both cheap delegate-instead-of-accept
changes), then scope and the rest.
